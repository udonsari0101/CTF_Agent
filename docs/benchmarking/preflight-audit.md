The private `benchmark_problems/` sibling directory contains inputs and oracle metadata; neither its answer records nor source trees belong in a public report or solver mount. See [protocol.md](protocol.md) for the validator's current two-arm schema.

The 23 static cases are distinct. Both manifests pass the current `_validate_manifest` schema check, and all 23 `cases/<id>/input` directories exist; this check did **not** inspect answer content or run a solver. The 17-case pilot covers crypto (4), forensics (5), reverse (5), and misc (3). The six Bronco development cases add crypto (3), forensics (1), reverse (1), and misc (1). The source catalogs retain upstream category strings such as `rev`, while the pilot manifest uses `reverse`; preserve the original label and add a separate analysis category rather than silently rewriting the source. The current eight holdout cases are too few, and none is a runnable web/pwn service case. `private_judge` in a manifest means that a judge record exists, not that an agent has obtained an accepted Flag. The local corpus, public corpus, and service candidates are inputs to a future experiment, not evidence of current solve rate.

The private `source-lock.json` pins CTFTiny, NYU CTF Bench, and Cybench revisions; the catalogs record source URLs, input hashes, answer exposure, and redistribution caveats. Those records provide traceability. They do not establish that upstream challenges may all be republished. The public [CTFTiny](https://github.com/NYU-LLM-CTF/CTFTiny), [NYU CTF Bench](https://github.com/NYU-LLM-CTF/NYU_CTF_Bench), and [Cybench](https://github.com/andyzorigin/cybench) repositories are the primary source for the respective source layout and licenses. Public answers and write-ups may already be indexed, so a holdout split protects against **our tuning**, not model pretraining or web retrieval.

## Coverage to add before a broad performance claim

| Missing or weak stratum | Why it matters | Admission test, without tailoring a prompt to one challenge |
|---|---|---|
| Runnable web and pwn services | Static files do not measure browser behavior, socket interaction, remote startup, or crash-driven iteration. | First run the three service candidates in an isolated network. Prove clean reset, reachable endpoint, correct independent oracle, and no answer-bearing source mount. Add more holdout cases from distinct events only after this works. |
| Kernel / unusual runtime / non-x86 | A Linux userspace ELF does not exercise QEMU, kernel module privilege boundaries, architectures, or resource limits. | Use legally reusable self-contained fixtures with frozen VM/image digest and a deterministic judge; measure startup cost separately. Avoid equating a host privilege requirement with permission to alter the host. |
| Large binary, memory, and filesystem pressure | A small handout can pass while GB upload, decompression, image storage, or solver OOM fails. | Add a synthetic large-input operations fixture with no answer-bearing artifact; classify it as reliability, not solve accuracy. Measure peak bytes and recovery. |
| GUI/mobile/audio/forensics variants | Current static selection has forensics but no proven GUI/Android/audio tool path; the local audio candidate lacks a complete statement/oracle. | Admit only after a reproducible input and independent verdict exist. Run tool-presence and representative-file smoke before spending model quota. |
| Blockchain, AI/ML, mixed, and unknown categories | No current pilot case can test those playbooks or nonstandard CTFd labels. | Add a small, independent sample only when rights and oracle are clear. Keep the upstream label; use the same neutral triage prompt across all arms. |
| Related challenges and clones | Shared notes or previously solved Flag can contaminate a nominally fresh trial. | Treat clones as repetitions of one case. Pre-register dependency groups; either isolate each problem completely or supply the **same explicitly selected, provenance-tagged evidence** to both arms. Never use a dependent challenge as an independent holdout unit. |
| Live or newly authored tasks | Public cases can be solved by finding existing answers. | Reserve an authorized live/new set for external validity, with competition limits and a dated official verdict. Do not use it to tune candidate rules. |

Adding one specimen per missing stratum is an apparatus check, not statistical coverage. A field-level claim needs multiple independent challenges per field and event, with uncertainty reported at the **challenge** level. Tool packs such as REA, SageMath, or extra web scanners are candidates only when an admitted case demonstrates a concrete capability gap; an installed binary alone is not a performance improvement.

## Source-code comparison: transfer the invariant, not the architecture

| Primary implementation or study artifact | Verifiable mechanism | CTF Agent experiment boundary |
|---|---|---|
| [D-CIPHER planner/executor](https://github.com/NYU-LLM-CTF/nyuctf_agents/blob/612190f/nyuctf_multiagent/agent.py#L2104-L2189) | Delegation creates an executor with a new conversation and returns a summary to the planner; the loop has a cost cap. | Compare a single default CLI with the existing solver before attributing an improvement to delegation. Preserve child observations and their evidence references; a summary does not equal native session continuation. |
| [ctf-solver-agent message bus](https://github.com/yakisoba0728/ctf-solver-agent/blob/df5c4a1/src/ctf_solver/collaboration/message_bus.py) | Per-solver cursors distribute bounded sibling messages. | Only share owner-selected, current, provenance-tagged observations. An unverified message must not become another solver's accepted fact. Measure duplicate work and contamination as well as solves. |
| [Conly-Zy parallel executor](https://github.com/Conly-Zy/CTF-Agent/blob/ce033c3/internal/agent/parallel.go#L815-L936) | Worker count is bounded and tasks are coordinated through channels/context. | Compare capacity, queue time, process cleanup, and cost against current autoscaling. An arbitrary `maxWorkers` from that code is not a suitable machine-specific limit. |
| [CTFusion evaluation flow](https://github.com/kaist-hacking/CTFusion#architecture) | Per-agent results are isolated and only the first correct Flag is forwarded to a live scoreboard. | Keep local candidate, independent oracle acceptance, and external CTFd submission as separate events. In paired trials, disable production auto-submit and use independent judges or isolated service instances. |
| [coding-agent research artifact](https://github.com/krodalabs/coding-agent-research-artifact) and [paper](https://arxiv.org/html/2607.13085) | Reports direct comparisons with ordinary coding CLIs on a fixed web set, with the same model/budget in the study. | Make the unmodified provider CLI the B0 arm. Do not infer that extra CTF instructions always hurt, or that this web-only result ranks our full-field agent. |

These links identify methods to test, not borrowed code or measured gains in this repository. The [detailed source audit](../research/solving-performance-research.ko.md) records more candidates and contrasting evidence. GitHub stars and a repository's README claims are discovery signals; they do not substitute for a controlled run. No external framework should replace the existing solver/skill structure simply because it has more agents or tools.

## Executable B0/B1 paired-trial contract

1. **Freeze and seal.** Select only cases with accessible handouts, an independent judge, and a pre-recorded input digest. Record provider, account type, model, reasoning/tier, exact CLI and image digests, network and tool profile, time/token budget, source publication status, and remote image fingerprint. Exclude the oracle and answer-bearing upstream source from each solver's filesystem and retrieval index.
2. **Equal task and environment.** B0 starts the unmodified Codex/Claude CLI in the same solver image as B1 with only the frozen challenge statement/files, target coordinates if required, and a minimal answer-delivery instruction. B1 uses the service's normal prompt/skills/notes and event plumbing. Both get the same shell/browser/tool permissions, service reset, credential class, and external network policy. The neutral evaluator extracts a candidate from either arm and asks the **same independent judge**; it does not give B0 hidden hints or give B1 a different verdict route.
3. **Schedule before seeing outcomes.** Generate the deterministic AB/BA plan in `protocol.md`. Isolate directories, provider session/config state, cookies, target service instance, and previous trial notes for every attempt. Run the scheduled order; if a service cannot support independent concurrent instances, serialize it and record remote drift. Never treat the two arms of one problem as independent problem samples.
4. **Use one start boundary.** Record both end-to-end latency from run request and active solve latency after workspace/provider readiness. `solve_wall_seconds` should refer to the same active-start event in both arms; queue, staging, startup, first response, tool time, remote wait, Flag observation, independent acceptance, and write-up remain separate timestamps. A failed/timeout attempt is censored at the registered budget, not a fast solve. If either arm needs human steering, log it and retain the pair.
5. **Keep the result auditable.** Save redacted event/transcript hashes, output artifact hashes, oracle evidence reference, provenance (`remote`, `artifact`, `web_search`, etc.), interventions, tokens/cost availability, and categorized failure. A Flag-like string or manual completion is not `accepted`. Record browser retrieval of a known public answer separately from a reproduced exploit.
6. **Stage candidates separately.** The current planner/reporter support only `baseline` and `harness`; run B0/B1 first. A candidate Cᵢ needs a new preregistered experiment or an extended schema with an explicit change ID and, for tool packs, an intentionally different tool/image digest. Do not force Cᵢ into a B0/B1 result by changing both prompt and tools at once.

The static preparation, paper review, offline schema checks, and CLI `--help`/tool smoke can finish without model quota. A real B0/B1 outcome, provider-native session/compaction in a live turn, oracle-accepted solves, latency/token comparison, Ultra advantage, and final image tool usefulness are **benchmark- or runtime-dependent**. They remain unmeasured until a frozen image and authorized credentials are available. Do not mark a prepared corpus or a passing report-validator test as a successful CTF benchmark.
